When is delta all-gather (sharded diff) necessary?

Two weight-sync paths: NCCL and Disk. When PP-level and TP-level sharded diff are needed.

Background

Two months ago, Changyi Yang and I added delta weight sync support to verl.

Besides reducing the trainer → rollout payload, our implementation also performs sharded diff: compute the diff on the shards first, then gather only the delta, instead of gathering full weights before computing the diff.

When is this necessary? We consider two paths: NCCL, where weights are AllGathered to one node before broadcast to rollout, and Disk, where PP nodes write to storage in parallel. The discussion assumes a large model distributed across PP nodes, with TP communication staying within each node.

The decision depends on two things: whether one node's CPU RAM can hold the gathered weights, and whether full AllGather becomes the bottleneck after delta compression reduces the output payload.

TL;DR

  • Both NCCL and Disk require PP-level sharded diff.
  • For NCCL, TP-level sharded diff is not required, but recommended.
  • For Disk, TP-level sharded diff is not required.

Two levels of sharded diff

PP-level: do not gather full weights across PP nodes. Each PP node computes the diff for its own portion, then sends or writes its delta. Full AllGather can still happen inside each node.

TP-level: each TP rank computes the diff on its local shard, so even node-local AllGather gathers only the delta.

In other words, PP-level sharded diff avoids cross-node full-weight gathers; TP-level sharded diff also reduces node-local gather traffic.

1. NCCL: AllGather to one node, then broadcast

PP nodes → gather to one source node → broadcast to rollout

PP-level sharded diff is required. Gathering the full model onto one node can exceed its CPU RAM (computing the diff requires keeping a pinned copy of the previous step's weights): a 1T-parameter BF16 model alone is about 2 TB. The cross-node gather also uses the network, just like trainer → rollout transfer. If we compress only the latter, the full gather becomes the new bottleneck. Compute the diff within each PP node and gather the deltas instead.

TP-level sharded diff is not required, but recommended. Node-local NVLink is fast, but a sufficiently small delta can make the output transfer faster than a full local gather. For example, with 300 GB of weights, an effective local gather bandwidth of 300 GB/s gives a 1 s gather. A 1% delta sent at 30 GB/s takes only 0.1 s. Making the local gather delta-aware helps avoid that bottleneck.

2. Disk: PP nodes write to storage in parallel

Each PP node: local TP AllGather → diff → write delta to storage

PP-level sharded diff is required. Each PP node handles its own weights and writes its own delta, avoiding a full-model snapshot on a single node.

TP-level sharded diff is not required. Full node-local NVLink AllGather is usually much faster than writing the delta to disk or object storage. For example, gathering 200 GB at 300 GB/s takes about 0.67 s; writing a 10% delta at 5 GB/s still takes 4 s. Storage remains the larger cost, so full local AllGather followed by diff is usually sufficient.

For a concrete disk-based implementation, see Slime's Delta Weight Sync documentation. It describes computing a diff for each gathered HF tensor, encoding and compressing the result, and publishing it through disk transport. The PP/TP recommendations here are our analysis of the topology and bottlenecks.

Conclusion

Path PP-level sharded diff TP-level sharded diff
NCCL: AllGather to one node → broadcast Required Not required, but recommended
Disk: PP nodes write in parallel Required Not required

背景

两个月前，我和Changyi Yang一起给verl支持了delta weight sync。

除了减少 trainer → rollout 的传输 payload，我们的实现还做了 sharded diff：先在 shard 上算 diff，再只 gather delta，而不是先 gather 完整权重再算 diff。

什么时候需要这样做？我们只讨论两种情况：NCCL（AllGather 到一个 node，再 broadcast 给 rollout）和 Disk（各 PP node 并行写 storage）。这里考虑的是大模型跨 PP node 分布、TP 通信留在单机内部的场景。

判断主要取决于两点：单个 node 的 CPU RAM 能否装下 gather 后的权重，以及 delta 压缩输出 payload 后，全量 AllGather 会不会成为新的瓶颈。

TL;DR

  • NCCL 和 Disk 都必须做 PP-level sharded diff。
  • NCCL：TP-level 非必须，建议做。
  • Disk：TP-level 非必须，可以不做。

两种粒度的 sharded diff

PP-level： 不跨 PP node gather 完整权重。每个 PP node 对自己的部分算 diff，再发送或写出自己的 delta；机器内部仍然可以做全量 AllGather。

TP-level： 每个 TP rank 直接对自己的 local shard 算 diff，即使是单机内部的 AllGather，也只 gather delta。

也就是说，PP-level 避免跨机 gather 完整权重；TP-level 则进一步减少单机内部的 gather 数据量。

1. NCCL：AllGather 到一个 node，再 broadcast

各 PP node → gather 到一个 source node → broadcast 给 rollout

PP-level sharded diff 必须做。 完整模型聚合到一台机器，CPU RAM 可能放不下（由于要算 diff，所以必须 pin 一版上个 step 的权重）：1T 参数的 BF16 模型，仅权重就约 2 TB。同时，跨 PP node 的 gather 和 trainer → rollout 都走跨机网络。如果只压缩后者，前面的全量 gather 就会成为新瓶颈。因此，应该先在各 PP node 内算 diff，再聚合 delta。

TP-level sharded diff 非必须，建议做。 单机 NVLink 虽然快，但 delta 足够小时，输出传输仍可能比全量 local gather 更快。例如，300 GB 权重以 300 GB/s 的有效带宽做 local gather，需要 1 s；如果 delta 只有 1%，以 30 GB/s 发送只需 0.1 s。让单机内部也只 gather delta，可以避免这一步成为瓶颈。

2. Disk：各 PP node 并行写 storage

每个 PP node：单机 TP AllGather → diff → 写 delta 到 storage

PP-level sharded diff 必须做。 各 PP node 只处理自己的权重、写出自己的 delta，避免在一个 node 上保存完整模型 snapshot。

TP-level sharded diff 非必须，可以不做。 单机 NVLink 全量 AllGather 通常远快于把 delta 写到 disk / object storage。例如，200 GB 权重以 300 GB/s gather，只需约 0.67 s；即使 delta 只有 10%，以 5 GB/s 写出仍需 4 s。主要开销仍在 storage，因此先做单机全量 AllGather，再算 diff，通常就够了。

具体的 disk 实现可以参考 Slime 的 Delta Weight Sync 文档：它介绍了对 gather 后的 HF tensor 计算 diff、编码压缩，再通过 disk transport 发布的流程。本文的 PP/TP 建议则是基于上述拓扑和瓶颈的分析。

结论

场景 PP-level sharded diff TP-level sharded diff
NCCL：AllGather 到一个 node → broadcast 必须 非必须，建议做
Disk：各 PP node 并行写 storage 必须 非必须
