When is delta all-gather (sharded diff) necessary?

Two levels of sharded diff. Four weight-sync topologies. A practical look at memory and communication bottlenecks.

Background

While looking at VeRL's delta weight sync implementation, we noticed something interesting:

VeRL does more than reduce the trainer → rollout transfer payload. It also performs sharded diff.

Instead of first AllGathering the full weights onto one rank and then computing the delta, it computes the diff on each shard first and gathers only the delta.

This article asks:

When is sharded diff necessary, and when can we skip it?

The answer mainly depends on two factors:

  1. Whether a single node has enough CPU RAM to hold the full weights after the gather.
  2. Whether AllGather takes longer than the delta-compressed trainer → rollout transfer—in other words, whether AllGather becomes the new bottleneck.

We will discuss four cases:

NCCL:
1. Cross-node AllGather to one node → that node broadcasts to rollout
2. Node-local AllGather within each PP stage → PP nodes send P2P to rollout

Disk:
3. Cross-node AllGather to one node → that node writes to disk / object storage
4. Node-local AllGather within each PP stage → PP nodes write to disk / object storage in parallel

TL;DR

  • PP-level sharded diff is essentially required. Otherwise, a very large model needs a full-weight gather across PP nodes, which is slow and may exceed a single node's CPU RAM.
  • TP-level sharded diff is optional for NCCL, but recommended. When the delta is very small, a full node-local AllGather can become the bottleneck again.
  • TP-level sharded diff is usually unnecessary for the disk path. Node-local NVLink AllGather is usually much faster than writing to disk / object storage.

Two granularities of sharded diff

Sharded diff can be divided into two levels.

1. TP-level sharded diff

This is the finest granularity.

Each TP rank computes the diff directly on its own shard:

TP rank 0 → diff ─┐
TP rank 1 → diff ─┤
TP rank 2 → diff ─┼→ gather delta
...               │

Even when these TP ranks are on the same machine, they gather only the delta rather than the full weights.

2. PP-level sharded diff

A full AllGather can still happen within each machine:

TP shards
   ↓
node-local full AllGather
   ↓
PP source
   ↓
diff

But there is no full-weight gather across PP nodes.

Each PP node keeps only its own portion or sends only its own delta:

PP0 → delta ─┐
PP1 → delta ─┤
PP2 → delta ─┼→ downstream
...          │

So:

TP-level sharded diff optimizes AllGather within a node.

And:

PP-level sharded diff avoids full-weight gathers across nodes.

1. NCCL weight sync

1.1 PP-level sharded diff: required

Suppose we do not use PP-level sharded diff:

PP0 ─┐
PP1 ─┤
PP2 ─┼→ cross-node gather to one node
...  │
     ↓
full model
     ↓
broadcast to rollout

This creates two problems.

Problem one: the weights may not fit in CPU RAM

For example, a 1T-parameter BF16 model needs:

1T × 2 bytes ≈ 2 TB

If the full weights must be materialized on one node, that node may need terabytes of CPU RAM.

This alone may make the design infeasible.

Problem two: cross-node AllGather becomes the new bottleneck

Both the trainer-side AllGather across PP nodes and the trainer → rollout transfer use the cross-node network.

For example:

cross-node gather bandwidth = 30 GB/s
trainer → rollout bandwidth = 30 GB/s
delta density               = 10%
full weights                = 1 TB

Then:

full cross-node gather:
1000 / 30 ≈ 33 s

delta trainer → rollout:
100 / 30 ≈ 3.3 s

If we optimize only trainer → rollout, the trainer-side full gather immediately becomes the new bottleneck.
In this case, PP-level sharded diff is required.

This is also an important reason why VeRL's delta_sharded can deliver substantial benefits.

1.2 TP-level sharded diff: optional, but recommended

If the path has already become:

TP shards within a PP stage
   ↓
node-local NVLink AllGather
   ↓
PP source
   ↓
RDMA P2P
   ↓
rollout

then full AllGather happens only within a node.

Assume:

NVLink AllGather = 300 GB/s
RDMA             = 30 GB/s
delta density    = 10%

For 300 GB of weights:

full local AllGather:
300 / 300 = 1 s

delta RDMA:
30 / 30 = 1 s

The two stages are roughly balanced.

So TP-level sharded diff is not strictly required.

But it is still recommended.

If delta density falls further to 1%:

delta RDMA:
3 GB / 30 GB/s = 0.1 s

while full local AllGather still takes:

300 / 300 = 1 s

then node-local AllGather becomes the bottleneck again.

For the NCCL path:

PP-level sharded diff is required; TP-level sharded diff is optional, but provides more headroom.

2. From disk / object storage

2.1 Cross-node gather to one node: PP-level sharded diff is still required

If the path is:

PP0 ─┐
PP1 ─┤
PP2 ─┼→ one node
...  │
     ↓
full model
     ↓
disk / S3

then even before considering performance, there is a direct problem:

The full model may not fit in a single node's CPU RAM.

For a model at the 1T-parameter scale, PP-level sharded diff / distributed writes remain very important.

A more reasonable design is:

PP0 → storage
PP1 → storage
PP2 → storage
...

rather than collecting everything on one node first.

2.2 Node-local AllGather within each PP stage: TP-level sharded diff is usually unnecessary

If the path already looks like the Slime-style design:

TP shards within a PP stage
   ↓
node-local NVLink AllGather
   ↓
PP source
   ↓
diff
   ↓
disk / S3

then the benefit of TP-level sharded diff is usually small.

For example:

PP stage weights = 200 GB
NVLink AllGather = 300 GB/s
storage write   = 5 GB/s

Then:

AllGather:
200 / 300 ≈ 0.67 s

storage write:
200 / 5 = 40 s

Even if AllGather improves from:

0.67 s → 0.07 s

the overall speedup is small.

So:

For the disk path, if the gather within each PP stage uses only node-local NVLink, TP-level sharded diff is usually unnecessary.

This is an important difference from the NCCL path.

With NCCL:

NVLink: hundreds of GB/s
RDMA:   tens of GB/s

The difference is often only about one order of magnitude.

But disk / object storage often provides only:

a few GB/s per node

which is much slower than NVLink.

The disk path is therefore more likely to be limited by storage bandwidth than by node-local AllGather.

Conclusion

Scenario PP-level sharded diff TP-level sharded diff
NCCL: cross-node gather → single-node broadcast Required Recommended
NCCL: node-local PP gather → P2P rollout Must preserve the distributed PP layout Optional, but recommended
Disk: cross-node gather → single-node storage write Required Secondary value
Disk: node-local PP gather → parallel storage writes Must preserve the distributed PP layout Usually unnecessary

The core decision comes down to two points:

Avoid full-weight gathers across PP nodes where possible: the weights may not fit, and the gather can become a cross-node communication bottleneck.

Whether to optimize a full node-local TP AllGather with sharded diff depends on how fast the output path is: it is worth considering for NCCL P2P, and usually not worthwhile for disk / object storage.

什么时候需要 delta all-gather（sharded diff）？

背景

在看 VeRL 的 delta weight sync 实现时，我们发现一个有意思的点：

VeRL 不只是减少了 trainer → rollout 的传输 payload，它还做了 sharded diff。

也就是说，它不是先把完整权重 AllGather 到一个 rank，再计算 delta；而是先在 shard 上计算 diff，再只 gather delta。

这篇文章主要想分析：

什么时候 sharded diff 是必要的，什么时候其实可以不做？

这主要取决于两个因素：

  1. 单个 node 的 CPU RAM 是否能装下 gather 后的完整权重。
  2. AllGather 的时间是否会超过 delta 后 trainer → rollout 的发送时间，即 AllGather 会不会成为新的瓶颈。

我们分四种情况讨论：

NCCL:
1. 跨机 AllGather 到单 node → 单 node broadcast 给 rollout
2. PP stage 内单机 AllGather → PP node P2P 发给 rollout

Disk:
3. 跨机 AllGather 到单 node → 单 node 写 disk / object storage
4. PP stage 内单机 AllGather → 多个 PP node 并行写 disk / object storage

TL;DR

  • PP-level sharded diff 基本必须做。 否则超大模型需要跨 PP node 聚合完整权重，不但慢，而且单机 CPU RAM 很可能放不下。
  • TP-level sharded diff 对 NCCL 可做可不做，但最好做。 当 delta 很小时，单机 full AllGather 也可能重新成为瓶颈。
  • TP-level sharded diff 对 disk path 通常没必要。 单机 NVLink AllGather 通常远快于写 disk / object storage。

两种粒度的 sharded diff

这里其实可以把 sharded diff 再细分成两层。

1. TP-level sharded diff

最细粒度。

每个 TP rank 直接对自己的 shard 算 diff：

TP rank 0 → diff ─┐
TP rank 1 → diff ─┤
TP rank 2 → diff ─┼→ gather delta
...               │

即使这些 TP rank 都在同一台机器上，也只 gather delta，而不是 full weight。

2. PP-level sharded diff

机器内部仍然可以做 full AllGather：

TP shards
   ↓
单机 full AllGather
   ↓
PP source
   ↓
diff

但是不同 PP node 之间不再 gather full weight。

每个 PP node 只保留自己的部分，或者只发送自己的 delta：

PP0 → delta ─┐
PP1 → delta ─┤
PP2 → delta ─┼→ downstream
...          │

所以：

TP-level sharded diff 优化的是 node 内 AllGather。

而：

PP-level sharded diff 避免的是跨 node 的 full-weight gather。

1. NCCL weight sync

1.1 PP-level sharded diff：必须做

假设我们不做 PP-level sharded diff：

PP0 ─┐
PP1 ─┤
PP2 ─┼→ 跨机 gather 到单 node
...  │
     ↓
完整模型
     ↓
broadcast rollout

这有两个问题。

问题一：CPU RAM 可能根本放不下

例如一个 1T BF16 模型：

1T × 2 bytes ≈ 2 TB

如果最终完整权重需要在一个 node 上 materialize，那么单机可能需要 TB 级 CPU RAM。

这本身就可能不可行。

问题二：跨机 AllGather 会成为新的瓶颈

trainer 侧跨 PP node 的 AllGather 和 trainer → rollout，本质上都走跨机网络。

例如：

跨机 gather bandwidth = 30 GB/s
trainer → rollout      = 30 GB/s
delta density          = 10%
full weight            = 1 TB

那么：

full cross-node gather:
1000 / 30 ≈ 33 s

delta trainer → rollout:
100 / 30 ≈ 3.3 s

如果只优化 trainer→rollout，trainer-side full gather 就会直接变成新瓶颈。
所以这种情况下，PP-level sharded diff 是必须做的。

这也是 VeRL delta_sharded 能获得明显收益的重要原因。

1.2 TP-level sharded diff：可做可不做，但最好做

如果已经改成：

PP stage 内 TP shards
   ↓
单机 NVLink AllGather
   ↓
PP source
   ↓
RDMA P2P
   ↓
rollout

这时候 full AllGather 已经只发生在 node 内。

假设：

NVLink AllGather = 300 GB/s
RDMA             = 30 GB/s
delta density    = 10%

对于 300 GB 权重：

full local AllGather:
300 / 300 = 1 s

delta RDMA:
30 / 30 = 1 s

两边基本平衡。

所以 TP-level sharded diff 不是绝对必须的。

但最好还是做。

因为如果 delta density 进一步降到 1%：

delta RDMA:
3 GB / 30 GB/s = 0.1 s

而 full local AllGather 仍然需要：

300 / 300 = 1 s

这时候 node 内 AllGather 反而会重新成为瓶颈。

所以 NCCL path 下：

PP-level sharded diff 必须做；TP-level sharded diff 可选，但做了更稳。

2. From disk / object storage

2.1 跨机 gather 到单 node：PP-level sharded diff 仍然必须做

如果是：

PP0 ─┐
PP1 ─┤
PP2 ─┼→ 单 node
...  │
     ↓
完整模型
     ↓
disk / S3

即使不考虑性能，也仍然有一个很直接的问题：

完整模型可能放不进单 node 的 CPU RAM。

所以对于 1T 级别模型，PP-level sharded diff / distributed write 仍然非常重要。

更合理的是：

PP0 → storage
PP1 → storage
PP2 → storage
...

而不是先汇总到一个 node。

2.2 PP stage 内单机 AllGather：TP-level sharded diff 基本没必要

如果已经是 Slime 这类路径：

PP stage 内 TP shards
   ↓
单机 NVLink AllGather
   ↓
PP source
   ↓
diff
   ↓
disk / S3

那么 TP-level sharded diff 的收益通常很小。

例如：

PP stage weight = 200 GB
NVLink AllGather = 300 GB/s
storage write    = 5 GB/s

那么：

AllGather:
200 / 300 ≈ 0.67 s

写 storage:
200 / 5 = 40 s

即使把 AllGather 从：

0.67 s → 0.07 s

整体也不会快多少。

所以：

Disk path 下，如果 PP stage 内部的 gather 只走单机 NVLink，那么通常没有必要再做 TP-level sharded diff。

这和 NCCL path 有一个重要区别。

NCCL 中：

NVLink: 数百 GB/s
RDMA:   数十 GB/s

差距通常只有一个数量级左右。

但 disk / object storage 往往只有：

几 GB/s / node

相比 NVLink 慢得多。

因此 disk path 更容易被 storage bandwidth bound，而不是被 node-local AllGather bound。

Conclusion

场景 PP-level sharded diff TP-level sharded diff
NCCL：跨机 gather → 单 node broadcast 必须 建议做
NCCL：PP node 内 gather → P2P rollout 必须保留分布式 PP layout 可选，但建议做
Disk：跨机 gather → 单 node 写 storage 必须 价值次要
Disk：PP node 内 gather → 并行写 storage 必须保留分布式 PP layout 通常没必要

最核心的判断可以简化成两句话：

跨 PP node 的 full-weight gather 应该尽量避免：它既可能放不下，也容易成为跨机通信瓶颈。

node 内 TP full AllGather 要不要继续做 sharded diff，则看后面的输出链路有多快：NCCL P2P 下值得考虑，disk/object storage 下通常不值得。
