Part 1 · Delta Weight Sync for verl

Motivation: Weight Sync in RL Could Be a Bottleneck

  • Traditional method: payload is the full model e.g. GLM-5: 744B params × 2 B (BF16) ≈ 1.5 TB per sync
  • On the critical path: Either the next rollout waits for the sync, or stale weights keep generating

Scenario 1

Training-Rollout in Same Cluster

effective bandwidth~25 GB/s
sync 1.5 TB≈ 1 min

~1 min vs. tens of minutes per RL step → not the bottleneck

Scenario 2

External Rollout

effective bandwidth~300 MB/s
sync 1.5 TB≈ 83 min

→ Rollout GPUs sit idle, or generation goes stale

Summary & Insights

Summary

  1. ProblemOff the RDMA fabric, weight synchronization becomes a bottleneck.
  2. ObservationIn BF16 or FP8, weight updates in RL are sparse.
  3. Naive implementationCPU RAM bottleneck, AllGather bottleneck.
  4. Optimization3.1× faster on 72B, lossless, works for both FSDP and Megatron.

Insight 1 · Why it matters

Cross-cluster rollout becomes practical

With weight sync no longer a bottleneck, trainer and rollout placement become independent choices: external rollout decouples training from inference.

Insight 2 · System design

Leverage the distributed setting of RL systems

Don't send all data to rank 0 or put all compute on rank 0: avoid the full gather, and reduce before any bytes move.

Part 2 · Zero-Drift Multi-Turn Tokenization

Tokenization: Three Principles

01

Token in, token out

SGLang consumes and returns token IDs, and the trainer gets exactly the sampled IDs. Text is never re-tokenized.

Why? Because decode-encode is not round-trip equal.

model generates

8264172

decode

"he"+"llo"

encode again

15339≠ the sampled IDs

02

Append-only encoding

Each prompt is the parent's tokens plus only the new messages. Parent tokens are reused as-is and never decoded.

parent tokens · reusednew
input_idsencode(messages[k:])

03

Model-specific boundary adapters

Turn-by-turn must equal one render of the whole conversation.

Part 2 · Zero-Drift Multi-Turn Tokenization

How to Support Multimodality at Scale

verl / Miles: tokenize in the controller

  1. 1Low parallelism: fetching big multimodal objects through Miles / agent server hits a bandwidth bottleneck.
  2. 2Big tensors hop across three processes, and Miles / agent server becomes a transfer bottleneck.

This design: tokenize inside SGLang

  1. 1Distributed rollout / trainer ranks fetch objects in parallel: no bandwidth bottleneck.
  2. 2Only light data passes through Miles / agent server: big tensors are fetched where they are consumed, not moved between processes.

Part 2 · Trajectory Representation & Tokenization

Insights

01

Trajectory representation

should be:

  1. Efficient
  2. Lossless: keep sub-agents, compaction, retries, etc.
  3. Lineage-aware: the data structure represents the lineage between trajectories, for customized reward assignment

02

Tokenization details decide training quality

It is important to implement zero-drift multi-turn tokenization to reduce training–inference mismatch.

03

Scale RL systems by separating control and data planes

RL systems are built around a single controller (a single driver). Large data should bypass it and be fetched where it is consumed, to avoid a transfer bottleneck.
